# Data and tools

**Goal:** a seeded database of fictional Dubai listings and the agent's tools, fully unit-tested without any model calls.

## Files to add/change

- `package.json`: add `drizzle-orm`, `@libsql/client`; dev: `drizzle-kit`, `tsx`. Scripts `db:generate`, `db:seed`.
- `drizzle.config.ts`
- `src/db/schema.ts`: tables (below)
- `src/db/client.ts`: `createDb(url)`, file DB for the app, `:memory:` for tests
- `src/db/migrations/`: generated by drizzle-kit (committed)
- `src/db/seed-data.ts` + `src/db/seed.ts`: 30 fixed listings
- `src/db/test-db.ts`: helper that creates a migrated, seeded in-memory DB for tests
- `src/tools/types.ts`: `AgentTool` type + `ToolContext` (`db`, `leadId`, `now`)
- `src/tools/*.ts`: one file per tool + `src/tools/index.ts` registry

## Data model

| Table      | Key fields                                                                                                                                                                                                                               |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `listings` | id, title, area, propertyType (apartment/villa/townhouse), beds (0 = studio), baths, sizeSqft, purpose (rent/sale), priceAed (yearly rent or sale price), status (ready/off_plan), handoverDate, furnished, features (JSON), description |
| `leads`    | id, purpose, areas (JSON), beds, budgetAed, timeline, financing (cash/mortgage), status (new/qualified/viewing_booked/handed_off), handoffReason, timestamps                                                                             |
| `viewings` | id, leadId, listingId, startsAt (UTC), status (booked/cancelled)                                                                                                                                                                         |

**Agent calendar is a rule, not a table:** one agent, Mon to Sat, 10:00 to 18:00 Dubai time (UTC+4, no daylight saving), 1-hour slots.
Free slots = rule minus booked viewings. Nothing to seed, and no stale slots.

**Seed data is fixed** (no random values), so evals are repeatable: about 30 listings across Dubai Marina, JVC, Downtown,
Business Bay, Palm Jumeirah, Dubai Hills, JLT and Arabian Ranches, with rentals and sales, ready and off-plan.

## Tools (what the model can call)

| Tool                  | Input                                                         | Returns                                                               |
| --------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------- |
| `search_listings`     | purpose, area?, beds?, maxPriceAed?, propertyType?, status?   | up to 5 matches (id, title, area, beds, price) or "no matches" + hint |
| `get_listing`         | listingId                                                     | full listing details, or "not found"                                  |
| `update_lead`         | any of: purpose, areas, beds, budgetAed, timeline, financing  | saved lead fields + which fields are still missing                    |
| `get_available_slots` | fromDate, days (1 to 7)                                       | free 1-hour slots (Dubai time)                                        |
| `book_viewing`        | listingId, startsAt                                           | booking confirmation, or "slot taken / outside hours / not found"     |
| `handoff_to_human`    | reason (negotiation/complaint/asked_for_human/other), summary | handoff confirmation; lead status becomes `handed_off`                |

`get_available_slots` is new compared to the first design: the model can't book a viewing well without knowing which
times are free.

## Design rules

- Each tool: Zod input schema with `.describe()` on every field, a description saying **when** to use it, and
  `run(input, ctx)`.
- **Time is injected** (`ctx.now`), never read from the system clock inside tools, so tests and evals are repeatable.
- "Nothing found" and "slot taken" are normal results with a clear message for the model, not exceptions.
- Prices come only from the database.

## Steps

1. ADR 0003 (libsql driver) → install packages → schema → generate migration → client + test DB helper.
2. Seed data + seed script; run it locally.
3. Tools one by one with the `add-agent-tool` skill: search_listings → get_listing → update_lead →
   get_available_slots → book_viewing → handoff_to_human. Each one gets tests before moving on.
4. Registry `src/tools/index.ts`; test that every tool has a unique name and a JSON-schema-compatible input.
5. `npm run check` green; reviewer subagent; mark this plan done.

## Tests

Per tool: happy path, invalid input rejected by the schema, the "nothing found / conflict" case. Plus:

- `book_viewing`: double booking rejected; Friday 09:00 (outside hours) rejected; a past time rejected.
- `get_available_slots`: Sunday has no slots; a booked slot disappears from the list.
- `update_lead`: partial updates merge and don't erase earlier fields.

## Risks / open questions

- **Eval cases are not written in this phase.** The eval format and runner arrive in Phase 4, so the tool-related
  cases (like the cash buyer in Dubai Marina) are added then. This differs from step 5 of the `add-agent-tool`
  skill, on purpose.
- **Weekend:** the plan assumes Sunday off (common for Dubai real estate agencies). Easy to change later.

**Status:** done (2026-11-15)

## Result

- `npm run check` green: **54 tests** (6 tools, registry contract, schema, seeding).
- ADR 0003 accepted. Migration `0000_init.sql`. `npm run db:seed` works and can be re-run.
- The cash-buyer case works at tool level: `search_listings` → only `L02` (AED 115,000); `update_lead` saves budget
  and cash, leaving `timeline` missing.

**Architecture review: needs changes → fixed.** 3 blocking issues, each now covered by a test:

1. `z.coerce.number()` turned `beds: null` into `0` (studio). → `execute()` treats `null`/`""` as "not provided".
2. Bookings had no time limit, and the label had no year (a booking in 2099 was confirmed as "Tue 17 Nov").
   → 60-day booking window in both calendar tools; labels always include the year.
3. `get_available_slots` cut the list at 24 slots but claimed the full range was checked. → `truncated` flag,
   `checked.to` = last day actually returned, message says later days weren't checked.

Suggestions applied: re-seeding upserts instead of delete + insert (deleting broke on booked listings); booking +
lead status saved in one atomic batch; the no-results hint now always appears; `get_listing` description no longer
implies every listing has a payment plan.

**Deferred to the next phase** (where the app first reads the database): validate `DATABASE_URL` with Zod in an app
config module; make sure migrations run from scripts/tests only, since `import.meta.url` paths change when Next.js
bundles server code.

**Also found and fixed:** the Stop hook failed because Claude Code passes `c:\...` (lowercase drive) and Vitest on
Windows then loads itself twice. The hook helper now uppercases the drive letter.
