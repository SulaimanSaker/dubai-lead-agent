# Evals

**Goal:** measure the agent on about 30 golden buyer conversations, on Claude Haiku 5.5 and on Gemma 3 4B, with
code checks on the **end state** (lead fields, bookings, handoffs, prices) and a calibrated LLM judge only for
tone and language. The result is a baseline table we can trust, so that Phase 5 (prompt v2, model choice) is
decided by numbers.

Follows Anthropic's eval guide (Claude API skill: `build-eval.md` + `eval-audit.md`): two human sign-offs (the
cases, then the grading), a pilot before any full run, infra errors kept apart from model failures, reps with a
noise estimate, and the real entry point, never a re-implemented call.

## What is evaluated

**One flow:** a buyer conversation through `handleBuyerMessage` (the same entry point the API route uses), so the
loop, guards, prompt v1, tools and adapters are all the real ones.

- Each `(case, rep)` runs in a **fresh in-memory database** with the 30 seed listings: no state leaks between runs.
- **Fixed "now"** (Mon 16 Nov 2026, 14:05 Dubai) unless a case sets its own: calendar answers are reproducible.
- **Scripted buyer messages**, sent in order. Limitation: the buyer doesn't adapt to what the agent asks, so later
  messages are written to make sense whatever the agent said ("Saturday at 11 works for me").
- Tracing stays on: every eval turn is a Langfuse trace tagged `eval` and the run id, so any failure can be opened.

## Cases (`evals/cases/`, validated with Zod)

```jsonc
{
  "id": "cash-buyer-marina-2bed",
  "description": "Buyer gives area, beds, budget and cash in one message",
  "tags": ["qualification", "en"], // tags[0] = category (report grouping)
  "source": "trace 2026-11-15 (Gemma dropped budget and cash)", // or "synthetic"
  "now": "2026-11-16T10:05:00Z", // optional
  "messages": ["Hi, looking for a 2 bed in Dubai Marina, budget around 120k a year, paying cash"],
  "expect": {
    "lead": {
      "purpose": "rent",
      "areas": ["Dubai Marina"],
      "beds": 2,
      "budgetAed": 120000,
      "financing": "cash",
    },
    "leadUnknown": ["timeline"], // must stay empty: no invented fields
    "toolCalls": [{ "name": "search_listings", "args": { "beds": 2 } }], // partial args
    "forbiddenTools": ["book_viewing"],
    "viewingBooked": false,
    "handoff": false,
    "language": "en",
  },
}
```

**Proposed set (~30), from real findings first, then synthetic variations:**

| Category                      | #   | Examples                                                                                                                                                                            |
| ----------------------------- | --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Qualification / extraction    | 8   | cash buyer Marina (real finding); mortgage villa purchase; "around 1.5M"; studio in JVC; two areas; details spread over 3 messages; typos; Arabic                                   |
| No invented fields            | 3   | greeting only (real: Gemma called `update_lead({})`); "just browsing"; budget only                                                                                                  |
| Search                        | 5   | no invented filters (real: Gemma added `apartment`, `ready`); no matches → explains what to relax; "tell me more" → `get_listing`; price asked → only from tools; off-plan question |
| Booking                       | 5   | picks a time → booked; "Saturday?" → offers slots but **doesn't book** (real: Gemma booked unasked); Sunday → explains closed; slot taken; no listing chosen yet                    |
| Handoff should happen         | 5   | asks for a person; asks for a discount; complaint; Arabic "I want an agent"; repeated confusion                                                                                     |
| Handoff should **not** happen | 3   | simple price question; "is it negotiable?" vs "give me 10% off" pair; general area question                                                                                         |
| Robustness                    | 2   | buyer states a wrong price ("Is L02 really 80k?") → not confirmed; "Thanks, bye" → polite, no tools (real: Gemma said "let's start")                                                |

Both directions are covered on purpose (handoff and no handoff, booking and no booking), so "always hand off" or
"always book" can't score well.

## Grading

Atomic checks, each `1`, `0` or not applicable (`null`) per case. **Code first; the judge only where code can't.**

| Metric               | How                | Pass when                                                                                                                  |
| -------------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `pass` (headline)    | code               | every applicable code check below passes                                                                                   |
| `extraction`         | code, DB end state | expected lead fields match (areas: contains) **and** `leadUnknown` fields are still empty                                  |
| `tool_use`           | code, transcript   | each expected tool call appears with the given args (partial match), no forbidden tool                                     |
| `booking`            | code, DB end state | a viewing exists exactly when expected                                                                                     |
| `handoff`            | code, DB end state | lead status `handed_off` exactly when expected (precision and recall also reported)                                        |
| `no_invented_prices` | code               | every AED amount in replies appears in a tool result (independent of the runtime guard)                                    |
| `turns_ok`           | code               | every turn ended `replied` (no safe fallback, max steps, internal error)                                                   |
| `tone`               | LLM judge          | reply language matches the buyer's; short (WhatsApp); at most 2 questions; no tool names or tags like `[END_CHAT]`; polite |

- **Judge:** a checkable rubric (claims, not a 1–5 vibe score), structured output, transcript treated as untrusted
  data, one call per case, judge cost recorded separately. **Calibration:** you hand-label about 10 replies, we
  report agreement; below ~90% on clear cases, the rubric gets another round before its numbers count.
- **Side metrics per case:** latency per turn, model calls, tool calls, tokens (incl. cache), cost, price-guard
  events, and the model that actually answered.

## Runner (`evals/run.ts`, run with tsx)

```
npm run evals -- --provider claude|local [--model …] [--reps 3] [--case <id>] [--concurrency 4] [--variant baseline]
npm run evals:report      # report.html (Anthropic's build-report-lite.mjs, copied into evals/report/)
npm run evals:compare     # markdown table: Model | pass | extraction | tool use | booking | handoff | prices | tone | latency | cost
```

- Output: `evals/runs/<model>/<variant>/results.jsonl` (one row per case × rep, written as it completes, resumable),
  `traces/<case>_rep<k>.json` (full conversation, tool calls, results), `errors.jsonl` (infra failures: provider
  down after retries, rate limits, timeouts, served-model mismatch; never scored as model failures).
- Hard wall-clock ceiling per case; the served model is checked on every call.
- **Oracle and null checks before the first paid run:** grader unit tests on hand-built good and bad transcripts,
  and a `--provider null` agent (always replies "Hello") that must fail almost everything.
- `evals/` imports only `@/agent` modules (layer rule).

## Steps (with the two sign-offs)

1. Case schema + loader; write the ~30 cases → **you review all of them** (sign-off 1).
2. Graders + unit tests (oracle / null), runner, report.
3. Pilot: 5 cases × 1 rep on Haiku (~$0.02) → report with graded transcripts; you hand-label ~10 replies for the
   judge → **you confirm the grading** (sign-off 2). Measured cost and time from the pilot.
4. Full baseline: Haiku (3 reps), Gemma (1 rep; slow), with the measured estimate shown first.
5. Compare table, findings (which cases fail and why), docs, build log.

## Tests

Loader (bad case files rejected with a clear message), each grader on good / bad / not-applicable inputs, the
null agent failing, an induced provider error landing in `errors.jsonl` (not as a score), resume skipping finished
`(case, rep)` rows.

## Cost and time (to be replaced by pilot numbers)

Rough: Haiku ≈ $0.001 per buyer message → 30 cases × ~2.5 messages × 3 reps ≈ **$0.25**, plus the judge. Gemma:
free, but 10–60 s per message → 1 rep ≈ 30–60 minutes. The pilot replaces these guesses with measured numbers.

## Risks / open questions

- **Judge model:** Haiku 5.5 is now also the agent; a model grading itself tends to be too kind.
- **Case files:** one file per case = about 30 approval prompts from the protection hook; grouped files = fewer.
- **Noise:** 30 cases × 3 reps ≈ ±10 points on a pass rate; differences smaller than that are not real.
- **CI:** an on-demand GitHub Actions eval job needs a pushed repo and an API key secret → Phase 5.
- **Scripted buyers** can't follow a conversation that goes somewhere unexpected; such cases are flagged, not
  forced.

**Status:** DONE (2026-11-20; see Results below). Approved 2026-11-17: judge Claude Sonnet 5.5; one case file per category; Claude drafts all cases, human reviews every one. **Sign-off 1 (cases): approved 2026-11-17, all 31 cases as in `evals/CASES.md`.**

**Sign-off 2 (grading): approved 2026-11-20.** Headline `pass` = all code checks AND the judge's `answers` +
`grounded` (`code_pass` = code checks only), after the pilot showed a do-nothing agent passing 29% on code
checks alone (0% with the judge). Judge calibration on 10 pilot conversations × 3 criteria: **29/30 agreement
(97%)**; the one disagreement (`buyer-states-a-wrong-price`, `answers`: human yes, judge no) is kept as labelled,
so the judge is slightly stricter than the human on that reply. The judge's "no" side is covered by the null-agent
run (judge said no on all 9 do-nothing conversations).

**Judge v2 (approved 2026-11-20).** The full runs showed two judge flaws: it didn't see what the agent was told
(it called "AED 260,000 per year" and "Sunday is closed" invented, though both are in the prompt / tool
descriptions), and it graded text written next to tool calls, which the buyer never sees. v2 gets the agent's
system prompt, tool descriptions and turn context, and skips that text. All saved rows were re-graded without
re-running the agents (`npm run evals:rejudge`, $0.50 for 133 rows). Calibration stays 29/30 (97%).

## Results (real numbers, 2026-11-20)

`npm run evals:compare` → `evals/runs/COMPARISON.md` (judge v2, per case then over cases):

| Model                               | Cases × reps | Pass    | Code checks | Judge answers / grounded / professional | Latency / turn | Agent cost / case |
| ----------------------------------- | ------------ | ------- | ----------- | --------------------------------------- | -------------- | ----------------- |
| Claude Haiku 5.5                    | 31 × 3       | **92%** | 95%         | 95% / 97% / 100%                        | 2.7 s          | $0.00052          |
| Gemma 3 4B (LM Studio, 16K context) | 31 × 1       | **0%**  | 23%         | 6% / 55% / 74%                          | 20.1 s         | free              |
| Do-nothing agent                    | 9 × 1        | 0%      | 100%        | 0% / 100% / 100%                        | —              | —                 |

- 0 infra errors in all runs. Spend: Haiku run $0.49 (83 new rows), Gemma run (judge) $0.21, re-grade $0.50.
- Judge calibration: 29/30 (97%) vs human labels, before and after judge v2.
- Haiku's 7 failing rows: price guard blocks corrections and offers (5, `buyer-states-a-wrong-price`,
  `offers-a-lower-price`), one unsupported claim, one judge mistake. Gemma fails mostly on tool use (41%),
  extraction (27%) and turns that end in `tool_failures` / `max_steps` (39% ended normally).
- Decision for Phase 5: keep Haiku 5.5 for buyers. Fix the price guard (prompt / guard v2) and measure it with
  this suite as a new variant.
